# PlayMatch v0.7 开发与验收记录

日期：2026-10-21。范围：Steam 身份目录的全量/增量/周期对账、持久游标、独立同步进程、SQL分页查询和前端运行状态。

## 交付范围与关键边界

已实现面向官方 `IStoreService/GetAppList/v1` 的自动发现链路，而不是继续手工增加种子文件。新身份目录没有5,000条总量限制；单页最多5,000。默认初次 full、随后600秒增量、7天全量对账，启用需要服务端 Key 和持续运行的 `catalog-sync` 进程。

**本轮没有可用 Steam Web API Key，没有执行真实鉴权全量遍历或实际增量同步。** 代码通过确定性HTTP替身、真实SQL、浏览器和容器验证；没有把合成数量当作Steam全库数量。真实上游响应合同、覆盖量和更新时效仍待部署后验收。

`steam_directory_apps` 只存身份、名称和变更标记，与已有推荐资料表分离。发现记录缺少简介时明确显示待补全，不编造玩法/中文支持/售价。自动元数据补全及全库主题推荐未完成，当前默认可推荐资料仍48款，现有向量/推荐资料路径仍有原先限制。不是“配置Key之后所有游戏即可智能推荐”。

## 实际实现

密钥用SecretStr配置，只在请求头发送。固定公共主机、不跟随重定向、不输出原始上游错误。参数显式过滤游戏，分页严格校验AppID/名称/类型/结束标志；响应大小、请求时限、单页范围和共享每日请求额度有界。

每页UPSERT和游标同事务；领取时预记请求额度，数据库时钟和随机owner租约限制过期写入。网络不持有数据库事务。未完成周期不推进水位；失败保留游标，429/鉴权/网络错误进入可见退避。定期full保留本轮未出现的旧身份，不直接认定下架或删除收藏。保留最近200轮完成回执；最后一页摘要不是全量上游归档。

身份目录提供AppID/名称前缀搜索和SQL keyset分页；推荐资料的原 `/games` 也改为SQL筛选/COUNT/LIMIT/OFFSET，保留原JSON和ID。任意子串查询不声称全文索引性能。默认推荐workflow仍非全库检索。

新API只读返回实际发现/已有资料/待补全数量、同步时间、心跳、游标、失败和退避。配置启用不等于同步完成。独立同步进程与推荐worker分开，Compose新增可选profile而非强制无Key抓取。

## 100,000条容量冒烟试验，不是真实Steam覆盖

`scripts/benchmark_steam_directory.py`生成100,000个明确合成名称，经相同分页解析/事务提交路径入库，20页，每页5,000；重开数据库后读取尾部游标页、精确AppID及名称前缀。没有网络请求，没有创建推荐元数据。

最终托管PostgreSQL单次测量：入库19.477秒，3个查询合计0.033秒；Python3.12.15。字段 `metadata_created=0`、`network_requests=0`、`restart_read=true`。本地SQLite也完成相同数量的试验。

这些只证明这份实现能处理该合成身份规模；不是生产P95、并发吞吐、真实商店采集速度、全库推荐规模或覆盖率。未利用这些数字修改实时性承诺。

[首个托管run39628587775](https://github.com/volcano-code/PlayMatch/actions/runs/39628587775)后端339、PG38、十万条试验、前端23及构建通过，但浏览器22通过、1失败。新增故障测试错误假设了自动重试请求数；点击刷新后仍返回合成503，不能据此判断真实恢复。

仅将该测试改为显式 `unavailable` 开关：先验证失败状态，再恢复服务并点击刷新，要求显示真实未启用状态。没有删除用例、放宽超时、修改产品重试策略或调低验收条件。最终run39629292324重新完整运行，23浏览器全部通过。失败历史保留。
